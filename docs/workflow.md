# Процесс работы

Единый процесс для Claude Code и Codex: Claude Code подгружает его через `CLAUDE.md`, Codex - по ссылке из `AGENTS.md`. Карта проекта - `CLAUDE.md`, правила - `.claude/rules/`, роли - `.claude/agents/`, промпты - `docs/prompts/`.

**Порядок старшинства:** прямая просьба пользователя в этой сессии → действующий план (его границы и полномочия) → `CLAUDE.md` → этот файл → `.claude/rules/` → скиллы, роли агентов, `docs/prompts/` и README папок. Два исключения, которые план не снимает: запреты `.claude/rules/security.md` (их не снимает и просьба в чате) и push (раздел 7) с действиями из первого пункта раздела 8 - им нужно отдельное «да» пользователя при любом плане. Противоречие между файлами назови пользователю и уточни решение.

## 1. Старт: от того, что уже есть

Прочитай просьбу, ядро `business/INDEX.md`, активный план в `plans/` и состояние git. Выбери вход по фактам:

| Вход | Признаки | Ближайший полезный шаг |
|---|---|---|
| **Нет идеи** | «хочу что-то сделать», задачи нет | Выясни желаемый результат, опыт и ограничения; предложи 2-3 направления и дешёвую проверку спроса. Стек не выбирай. Направление выбрано - уточни его промптом `docs/prompts/grill-idea.md`. |
| **Есть идея** | описан продукт или задача, кода нет | Скилл `project-bootstrap`: ядро `business/INDEX.md`, Reality Check, стек, план результата. |
| **Есть архитектура** | документ архитектуры в репо или у пользователя | Прочитай и проверь цель, границы, реализуемость; дальше он источник плана. |
| **Есть код** | манифесты, `src/`, `app/`, тесты | Скилл `project-bootstrap`, режим IMPORT: отдели реализованное от обещанного, заполни ядро по коду, предложи следующий шаг. |
| **Продолжаем** | в `plans/` есть план со статусом не «завершён» и не «отменён» (`TEMPLATE.md` и `README.md` - не планы) | Сверь checkpoint плана с файлами, diff и тестами, продолжи незавершённое. Старт заново не запускай. |

Входы сочетаются: код плюс активный план - это продолжение. Спрашивай только о пробелах, которые меняют ближайшее решение: одно сообщение - один вопрос с 3-4 вариантами ответа. Ответ уже есть в файлах или в просьбе - используй его и назови источник.

Пользователь пришёл с конкретной задачей - начни с неё, адаптацию шаблона предложи после.

## 2. Второй мозг: ядро и файлы по мере данных

- **У проекта уже есть свой бизнес-индекс или документы** вне `business/` - они и есть источник: ядро ссылается на них, второй мозг рядом не заводится.
- **Ядро** - `business/INDEX.md`: что за проект, для кого, какую проблему решаем, текущая цель и её критерий, ограничения, тип проекта, приватность, подтверждённые факты, гипотезы, ближайший шаг. Неизвестное так и записывается: «неизвестно».
- **Файлы разделов появляются по мере данных**, из форм `templates/business/`: порядок и таблица «задача → файлы» - в `.claude/rules/business-context.md`.
- **Приватность до первой записи.** Перед записью бизнес-фактов пройди проверку из `.claude/rules/security.md` (раздел «Публичный репозиторий и business/») и запиши результат в ядро. Пока проверка не пройдена, в `business/` пишется только то, что можно опубликовать.
- Факт из кода - факт о коде: код оплаты не доказывает выручку или спрос.

## 3. Архитектура: один документ

Канонический документ - `docs/architecture/overview.md` или уже существующий документ проекта; его путь записан в `CLAUDE.md`. В нём границы системы, компоненты, данные, интеграции, ограничения. Решения с причинами - ADR в `docs/decisions/`. Планы ссылаются на архитектуру и не копируют её. Код разошёлся с документом - отметь расхождение явно и обнови источник.

## 4. План: один на результат

| Размер | Примеры | План |
|---|---|---|
| **S** | опечатка, цвет кнопки, ошибка типизации, обновление зависимости | без плана: правка → проверка → Self-Audit по критерию задачи |
| **M** | новая страница, форма с валидацией, интеграция с одним API | план по `plans/TEMPLATE.md`, ревью - по разделу 5 |
| **L** | схема БД, авторизация, смена фреймворка, многомодульный рефакторинг | план, 4 пункта из раздела 7 этого файла продуманы ещё на этапе плана, ревью обязательно |

Сомневаешься между размерами - бери больший.

- **Сначала найди действующий план** этого результата в `plans/` и внутри документов архитектуры. Нашёл - продолжай и дополняй его, второй план не заводи.
- **Один план - один согласованный результат.** Он может включать несколько функций и фаз и описывает весь путь до результата. Разные владельцы, сроки или критерии приёмки - разные планы.
- План пишется по `plans/TEMPLATE.md`: цель и критерий приёмки, границы и полномочия, лимиты, 10 причин провала, Challenge Loop, фазы с критериями и проверками, checkpoint.
- План с интерфейсом - прочитай `.claude/rules/ui-design.md`, план с деплоем - `.claude/rules/deployment.md`. Claude Code подгружает эти правила сам только при работе с файлами их темы.
- **Первая фаза нового продукта** - минимальный сквозной сценарий пользователя через реальные слои системы. Это часть будущего результата, а не выбрасываемая заглушка.
- План закрывается после итоговой приёмки (раздел 9 этого файла). Отменяется, когда цель потеряла смысл, ни один вариант не работает или цена несоизмерима с пользой: статус «отменён», причина в «Итоге», урок в `retrospectives/`.

## 5. Ревью плана и судья

**Когда:** план L - всегда; план M - по умолчанию тоже, пропуск допустим при малом риске и с согласия пользователя, дата, причина и согласие - в разделе 7 плана; S-задача идёт без плана и ревью. Эта норма одна для всех файлов шаблона. Промпт - `docs/prompts/run-critique.md`.

1. **Рецензенты по риску**, без квот. Им передаётся текстом всё, что нужно для проверки: план или diff, критерии, вывод проверок. `critic` - риски и соответствие целям, `architect` - реализуемость фаз, `ux-designer` - путь пользователя, `qa-tester` - проверяемость критериев, `researcher` - внешние факты, на которые опирается план.
2. **Каждая находка** - источник, последствие, исправление. Ноль находок допустим, выдумывать ради числа нельзя.
3. **Судья** (`judge`) проверяет каждую находку по источникам и решает: принять / отклонить / отложить, с причиной. Это проверка, а не голосование рецензентов.
4. Принятые правки внесены в план; исправленный блокер ревьюится заново - и в плане, и в фазе. Затем план показан пользователю, **одобрение записано в план**: кто, когда, какой объём.

Независимость - это отдельный агент, отдельная сессия или человек, а не автор плана. **Субагентов нет** (например, в Codex) - роли рецензентов и судьи выполняет сессия, которая план не писала, порядок - в `docs/prompts/run-critique.md`. До решений судьи ворота «не проверено», и план к одобрению не идёт. Самопроверка автора полезна, но независимой не считается.

## 6. Исполнение одобренного плана

Одобрение разрешает пройти **все фазы** плана в его границах без вопроса «продолжать?» после каждой. Прав на прод оно не добавляет (раздел 8).

Цикл каждой фазы:

1. **Тест до кода.** Падающий тест на новое поведение → минимальная реализация → рефакторинг при зелёных тестах (скилл `tdd`). Автоматический тест неприменим - заранее запиши проверяемый сценарий и причину.
2. **Проверки стека** - lint, typecheck, build, тесты: реальные команды и реальный вывод. Для бага - воспроизведение и регрессионный тест (скилл `diagnose`).
3. **Self-Audit** из плана: каждый критерий фазы закрыт и подтверждён.
4. **Независимое ревью** diff, критериев и доказательств (`critic` и `qa-tester`, по риску ещё `architect` или `ux-designer`), затем **судья**, даже при нуле находок. Diff и вывод проверок - рецензентам текстом. Субагентов нет - фаза остаётся без `[x]`, в checkpoint «ревью фазы ждёт отдельной сессии»; дальше тот же порядок по сессиям, что для плана (`docs/prompts/run-critique.md`).
5. **Исправления** принятого и повтор затронутых проверок.
6. **Checkpoint** в плане и `[x]` у фазы, если у судьи нет блокеров. `[x]` означает проверенные критерии, а не написанный код.

- Несколько исполнителей работают в разных файлах; после слияния их правок проверки идут на объединённом состоянии.
- **Лимиты** времени, стоимости и попыток исправления записаны в плане до старта. Остановись с checkpoint, когда лимит исчерпан, дефект повторяется без прогресса, проверка или зависимость недоступна, рядом чужие незакоммиченные правки (их нет в checkpoint и они не относятся к плану), появилась неоднозначность с заметными последствиями или работа выходит за одобренный объём. Спрашивай только конкретное недостающее решение.
- Незакоммиченные файлы плана перечисляются в checkpoint, чтобы следующая сессия не приняла их за чужие.
- В длинной фазе пиши промежуточный checkpoint. Запущенные процессы (dev-сервер, миграция, второй исполнитель) записывай: что, где, статус, как проверить. После паузы сначала проверь, жив ли прежний процесс и что он уже сделал, и только потом решай о повторном запуске.

## 7. Перед push, merge и деплоем: 4 пункта

Перед `git push`, слиянием в `main` и любым деплоем ответь на 4 вопроса и дай по каждому вердикт **ПРОХОДИТ / НЕ ПРОХОДИТ / НЕ ПРОВЕРЕНО**. В плане ответы живут в разделе «Проверка перед push».

1. **Регрессия.** Какие модули зависят от изменённых файлов? Прогнан весь набор тестов проекта, а не только тесты текущей фазы. Тест упал один раз - перезапусти и сравни с `main`: так видно, флакует набор или его сломали эти изменения.
2. **Side effects.** Изменился ли контракт: API, типы, схема БД, формат файлов, переменные окружения? Если да - кто его потребители и обновлён ли каждый. Потребителей вне репозитория (мобильное приложение, интеграции, чужие боты) назови отдельно: тесты репо их не проверят.
3. **Think ahead.** Что сломается через неделю или месяц? Пустые данные, очень большие данные, параллельные запросы, неожиданное действие пользователя - по каждому конкретный ответ.
4. **Совместимость.** Старый клиент с новым сервером и новый код со старыми данными. Нужна ли миграция данных, и можно ли запустить её повторно без вреда. Нужен ли флаг для постепенного включения - если нет, так и напиши.

**НЕ ПРОВЕРЕНО = красное**, как и НЕ ПРОХОДИТ. Пустой вывод, нулевой код возврата у инструмента, которому нечего было проверять, отсутствующий отчёт означают «не проверено», а не «чисто». Вердикт - не разрешение: push ждёт явного «да» пользователя (`.claude/rules/git.md`).

## 8. Границы полномочий

- **Отдельное явное «да» пользователя, проверка среды и план отката** нужны для: деплоя, миграций на проде, удаления данных, платежей, внешних публикаций, смены DNS и секретов, установки скиллов, MCP и расширений (`docs/prompts/install-skill-safely.md`). Одобрение плана и адаптация шаблона этих прав не дают.
- Разрешения `.claude/settings.json` действуют и внутри одобренного плана: на commit и push Claude Code спросит пользователя. Агент не включает bypass и не ослабляет разрешения ради автономности.
- Коммит - если его разрешает план или пользователь прямо попросил: проверен staged diff, файлы добавлены поимённо, чужих изменений нет (`.claude/rules/git.md`).
- Секреты не выводятся даже при диагностике (`.claude/rules/security.md`).

## 9. Завершение

1. Все фазы `[x]` → проверь объединённый результат по критериям всего плана («Итоговая приёмка»).
2. Изменились решения - обнови архитектуру, `business/` и `CONTEXT.md`.
3. Заполни «Итог» плана и поставь статус «завершён».
4. Ретроспектива по `retrospectives/TEMPLATE.md` - обязательно после закрытия плана; после обычной сессии - когда есть урок.
5. Отчёт пользователю: что работает, чем проверено, что осталось и почему. Незапущенные тесты, отсутствующее ревью и частичный результат называются прямо.
