# Промпт: ревью плана и судья

> Используйте, когда план готов, а код ещё не начат: перед одобрением плана M и L или после изменения его объёма. Рецензенты смотрят на план с тех сторон, где у него риск, судья проверяет каждую их находку по источникам. Один агент в одном чате плохо видит свою работу со стороны, независимые рецензенты и судья видят. Процесс - `docs/workflow.md`, раздел 5.

## Когда использовать

- План M или L написан, Challenge Loop заполнен, одобрения ещё нет.
- Изменились объём или полномочия уже одобренного плана.
- План L - всегда; план M - по умолчанию (норма - `docs/workflow.md`, раздел 5).

## Когда НЕ использовать

- S-задача без плана.
- Нужно проверить не план, а артефакт перед запуском (оффер, лендинг, схему деплоя) → [stress-test.md](./stress-test.md).

## Промпт

Лучше запускать в новом чате: так ревью не наследует рассуждений автора плана.

```
Ревью плана plans/<ИМЯ-ФАЙЛА>.md до реализации.

1. Прочитай план, ядро business/INDEX.md, канонический документ архитектуры и фактическое состояние кода и тестов. Прежние записи о ревью тоже - в разделе 7, для фазы в checkpoint: незакрытый блокер из них - находка. Повторное интервью не проводи, если ответы уже есть в файлах.

2. Выбери рецензентов по риску этого плана, без квот, и запусти их параллельно отдельными субагентами:
   - critic (.claude/agents/critic.md), режим ревью - риски и соответствие целям из ядра;
   - architect (.claude/agents/architect.md) - реализуемость каждой фазы, зависимости, раздел "Проверка перед push";
   - ux-designer (.claude/agents/ux-designer.md) - где пользователь застрянет; нет пользовательской части - не зови его и скажи об этом;
   - qa-tester (.claude/agents/qa-tester.md) - проверяемы ли критерии фаз и приёмки;
   - researcher (.claude/agents/researcher.md) - если план опирается на внешние факты.
   Каждая находка: источник, последствие, исправление. Ноль находок допустим.

3. Отдай все находки судье (.claude/agents/judge.md) отдельным субагентом, даже при нуле находок: судья ищет и пропущенный блокер. Решение принять / отклонить / отложить с причиной по каждой.

4. Принятые правки внеси в план, решения судьи - в раздел "7. Ревью плана и судья". Отложенные - туда же с пометкой. Судья нашёл блокер - после исправления повтори шаги 2-4 на исправление, и только потом шаг 5.

5. Покажи мне итоговый план, решения судьи и открытые вопросы. Попроси одобрения. Реализацию не начинай.

Пропуск ревью: только план M, при малом риске и с согласия пользователя - строка в разделе 7 с датой, причиной и тем, кто согласился. Тогда сразу шаг 5. После смены объёма прежний пропуск не действует.

Субагентов нет (например, Codex): ревью проводит другая сессия или человек - тот, кто не писал объект ревью (план или diff фазы). Ты его писал - остановись: ворота "не проверено", попроси меня открыть новую сессию для ревью. Не писал - выполни роли выбранных рецензентов, затем роль judge (даже при нуле находок) и запиши итог в раздел 7 плана, для фазы - в checkpoint: дата, роли, находки, решения судьи. Это единственная запись, которую разрешает режим ревью. Судья нашёл блокер - исправь его, и до шага 5 (для фазы - до [x]) нужно новое ревью исправления, снова другой сессией. Блокеров нет - шаги 4-5; для фазы - исправить принятое, повторить затронутые проверки и поставить [x]. Изменился объём - нужно новое ревью.
Самопроверку за независимое ревью не выдавай.
```

## Что должно получиться

- Находки рецензентов с источниками.
- Решения судьи по каждой, дубли объединены.
- Принятые правки в плане, раздел 7 заполнен.
- Итоговый план показан пользователю, Claude ждёт одобрения.
