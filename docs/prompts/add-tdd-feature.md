# Промпт: добавить функцию через TDD

> Используйте когда нужна чистая логика с понятным входом и выходом: расчёт, валидатор, парсер, конвертер, бизнес-правила. Запускает скилл `tdd` по циклу Red → Green → Refactor.

## Когда использовать

- Нужна чистая функция: вход → выход, без UI и без I/O.
- Бизнес-правило с известными случаями (скидки, лимиты, доступы).
- Багфикс, для которого хотите тест-страховку.

## Когда НЕ использовать

- UI-компонент (визуал важнее логики) — используйте обычный create-feature-plan + ручную проверку.
- Прототип на час, который выкинут.
- Простая правка конфига или копи.

## Промпт

```
Добавь функцию через TDD. Запусти скилл tdd
(.claude/skills/tdd/SKILL.md) и веди меня по циклу Red → Green → Refactor.

Что нужно: <ИМЯ ФУНКЦИИ + одно предложение, что она делает>
Сигнатура (если знаете): <вход → выход, типы>
Где живёт: <src/lib/<...> или другое>
Известные случаи:
- <вход 1> → <выход 1>
- <вход 2> → <выход 2>
- граница / ошибка: <вход> → <поведение>

Алгоритм для тебя:

1. Прежде всего — Challenge Loop (3 вопроса из .claude/rules/planning.md):
   - Решает ли это задачу?
   - Это лучший путь? Альтернативы?
   - Нет ли "кода ради кода"?
   Покажи мне ответы. Если на любой "не уверен" — обсуди со мной.

2. Цикл по одному случаю за раз. Сначала Happy path:
   - Red: напиши ОДИН тест на ожидание, прогони — он должен упасть.
   - Green: минимальная реализация, чтобы тест прошёл.
     Можно "прибить гвоздями", если это самое простое.
   - Refactor: убери дубли, дай нормальные имена. Тесты — зелёные.

3. Следующие случаи в том же порядке: граничные → ошибки → регрессии.
   После каждого — все тесты зелёные.

4. Не пиши все 5 тестов сразу. По одному. Жди мою реакцию между случаями
   только если возникает развилка по поведению.

5. После завершения:
   - Заполни Self-Audit (см. plans/TEMPLATE.md блок 10):
     цель закрыта, метрика проверена, ничего не "doоделаем потом".
   - Покажи команду запуска тестов локально.
   - Честно перечисли НЕ покрытые сценарии (не маскируй).

Anti-Rationalization: запрещено "тест проходит, потому что моки".
Запрещено зелёный из-за слабого ассерта. Тестируем поведение, не имплементацию.

Не делай git commit. Все ответы — на русском.
```

## Что должно получиться

- Один файл с тестами `<...>.test.ts` и один с реализацией `<...>.ts`.
- N зелёных тестов, покрывающих happy / границы / ошибки.
- Команда запуска тестов в чате.
- Список НЕ покрытых сценариев — честно.
- Self-Audit в плане (если был активный план для этой функции).
