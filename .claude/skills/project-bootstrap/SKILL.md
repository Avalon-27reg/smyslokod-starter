# Skill: project-bootstrap

Старт проекта на шаблоне `smyslokod-starter` от того, что у пользователя уже есть: идея, код или документ архитектуры. Результат - ядро `business/INDEX.md`, стек в `CLAUDE.md` и первый план результата, одобренный пользователем. Обязательной анкеты нет: вопросы задаются только о пробелах, которые меняют ближайшее решение.

Общий процесс - `docs/workflow.md`. Этот скилл - подробный порядок для входов «есть идея», «есть код» и «есть архитектура» из раздела 1 процесса.

## Когда применять

- Пользователь пришёл с идеей, кодом или документом архитектуры, а ядро `business/INDEX.md` в основном «неизвестно».
- Пользователь просит адаптировать шаблон или начать проект на нём.

## Когда НЕ применять

- В `plans/` есть план со статусом не «завершён» и не «отменён» - это вход «Продолжаем» (`docs/workflow.md`, раздел 1).
- Пользователь пришёл с конкретной задачей, не связанной со стартом, - сначала она (`docs/workflow.md`, раздел 1).
- Идеи ещё нет - это вход «Нет идеи» (`docs/workflow.md`, раздел 1): сначала направление, затем `docs/prompts/grill-idea.md`.

## Продолжение после перерыва

Отдельного журнала нет, состояние восстанавливается по фактам: что записано в ядре `business/INDEX.md` и в созданных разделах, есть ли черновик плана в `plans/`. Перечитай их, скажи одной фразой, что уже есть, и продолжи с первого незакрытого шага.

---

## Шаг 1. Собери факты

Прочитай просьбу пользователя, `business/INDEX.md`, разделы 1-2 `CLAUDE.md`, `docs/architecture/overview.md` и `plans/`. Проверь, есть ли код в корне: `package.json`, `pyproject.toml`, `requirements.txt`, `go.mod`, `Cargo.toml`, папки `src/` или `app/`. Документ архитектуры пользователь мог приложить или назвать путь к нему.

Путь: **ИДЕЯ**, если кода и архитектуры нет; **IMPORT**, если есть код или документ архитектуры (раздел «Режим IMPORT» ниже).

**Готово, когда** ты одной фразой сказал пользователю, что понял, и назвал путь. Пользователь может поправить.

## Шаг 2. Приватность

До записи первого бизнес-факта пройди проверку из `.claude/rules/security.md`, раздел «Публичный репозиторий и business/». Для публичного репозитория там же - отдельный коммит `.gitignore` и снятия `business/` с учёта: это единственный коммит до одобрения плана, и только с согласия пользователя.

**Готово, когда** строка «Приватность» в ядре больше не «не проверено».

## Шаг 3. Ядро и глубина

Заполни ядро `business/INDEX.md` тем, что уже есть в просьбе, коде и документах, со ссылкой на источник. Затем спроси недостающее - только то, что меняет ближайшее решение. Для выбора глубины нужны 4 сигнала; спрашивай только те, которых ещё нет:

1. **Срок до первого пользователя:** (а) 1-3 дня, (б) 1-4 недели, (в) 1-3 месяца, (г) 3+ месяца.
2. **Регистрация, платежи, персональные данные:** (а) ничего, чистый просмотр; (б) только email или имя; (в) платежи и/или ПДн.
3. **Факты про аудиторию:** (а) почти ничего, гипотеза; (б) общее представление; (в) реальные интервью или продажи.
4. **Тип проекта:** (а) коммерческий - продаёшь продукт или услугу; (б) внутренний инструмент компании или команды; (в) личный, open-source или обучающий.

| Сигналы | Глубина |
| ------- | ------- |
| Срок < 1 недели **И** без платежей **И** аудитория = гипотеза | **MINIMAL** |
| Срок 1-4 недели **ИЛИ** только email/имя **ИЛИ** общее представление | **LITE** |
| Срок 1+ месяц **ИЛИ** платежи / ПДн **ИЛИ** реальные интервью | **FULL** |
| Сигналы конфликтуют (например: 3 дня, но платежи) | Объясни конфликт и рекомендуй на полшага выше |

Назови глубину и обоснование одной строкой, запиши её в ядро. Пользователь может сменить её словами: «минимально», «по-полной».

Правила вопросов:

- Одно сообщение - один вопрос, к нему 3-4 варианта, собранных из того, что пользователь уже рассказал. Он выбирает номер, пишет свой вариант или «не знаю».
- «Не знаю» - предложи свой вариант и спроси «согласен?».
- Факт без источника записывается в «Гипотезы», а не в «Подтверждённые факты».

**Готово, когда** строки ядра «Проект», «Для кого», «Проблема», «Цель сейчас и критерий», «Тип проекта» и «Глубина» заполнены, а у каждого оставшегося «неизвестно» есть вопрос в «Открытых вопросах».

## Шаг 4. Разделы по глубине

Файл раздела создаётся из формы `templates/business/<путь>` только тогда, когда для него есть данные (`.claude/rules/business-context.md`).

| Глубина | Что выяснить сверх ядра | Файлы из форм |
| ------- | ----------------------- | ------------- |
| **MINIMAL** | первый видимый результат за одну сессию; где хостить; что нельзя трогать | `products/overview.md` (абзац для лендинга), `audience/avatar.md` (блоки «Кто это» и «Боли») |
| **LITE** | один сегмент аудитории, главная боль, формат продукта, монетизация, 1-2 канала привлечения, бренд, если он есть | всё из MINIMAL + `products/pricing.md`, `audience/objections.md`, `goals/monthly.md`, `marketing/channels.md`, `assets/brand-guidelines.md` |
| **FULL** | юрисдикция и ПДн, базовая экономика (цена, стоимость привлечения клиента), 2-3 конкурента, нужные интеграции, бренд и референсы, команда | всё из LITE + `company/`, `audience/segments.md`, `audience/journey.md`, остальные `goals/`, `economics/`, `marketing/competitors.md`, `marketing/content.md`, `marketing/funnel.md`, остальные `assets/` |

**Reality Check** - в LITE и FULL, как только известны продукт, формат и монетизация. Назови одним абзацем 2-3 конкретных риска из услышанного: объём переоценён (маркетплейс за неделю), нет первого клиента, нет канала, конкурент закрывает задачу лучше, ценность размыта. Затем: «Это дыры, которые надо закрыть, а не приговор идее. Обдумаем сейчас или продолжаем?». Ответ «обдумать» - запиши риски в «Открытые вопросы» ядра и остановись. В MINIMAL главный риск записывается в ядро одной строкой.

**Некоммерческий проект** (ответ (б) или (в) на сигнал 4): аудитория - те, кто пользуется, и тот, кому важен результат; ценность - сэкономленное время, меньше ошибок, знания. Файлы юнит-экономики, выручки, прогноза, воронки, конкурентов и отзывов не создаются; ядро отмечает продажи, воронку и юнит-экономику как неприменимые. `products/pricing.md` при необходимости описывает, как пользователь получает доступ, а `economics/costs.md` - сколько стоит поддержка.

**Готово, когда** каждый файл из списка глубины создан с данными или не создан, а причина записана в «Открытые вопросы» ядра.

## Шаг 5. Стек

В IMPORT стек известен из кода. Иначе задай один вопрос:

> «Какой стек ставим для этого проекта?»
> (а) Next.js + TypeScript + Tailwind + shadcn/ui (web-MVP / лендинг / SaaS)
> (б) Python + FastAPI / Django (бэкенд / API / админка)
> (в) Telegram-бот (aiogram на Python или Telegraf на Node)
> (г) Vite + React / Vue / Svelte (SPA без SSR)
> (д) React Native / Expo (мобильное)
> (е) Что-то другое - расскажи свободным текстом
> (ж) Без кода - контент-проект, документация, методология

Запиши стек одной строкой в раздел 2 `CLAUDE.md`, обоснование - в таблицу стека `docs/architecture/overview.md`. Ничего не устанавливай: установка - первая фаза плана, она выполняется после одобрения.

**Готово, когда** в разделе 2 `CLAUDE.md` записан стек или «без кода».

## Шаг 6. Карта, словарь, первый план

- Раздел 1 `CLAUDE.md`: один абзац - что за проект и для кого, вместо текста о шаблоне.
- `CONTEXT.md`: термины предметной области из разговора или кода, по строке на термин.
- Первый план по `docs/workflow.md` (раздел 4) и `plans/TEMPLATE.md`. Результат - первый видимый результат пользователя (в IMPORT - главный пробел из Reality Check). Первая фаза - минимальный сквозной сценарий через реальные слои; установка стека входит в неё. Границы, полномочия и лимиты заполнены.
- Ревью плана с судьёй - по норме `docs/workflow.md`, раздел 5: план L - всегда, план M - по умолчанию, пропуск только при малом риске, с согласия пользователя, с датой, причиной и согласием в разделе 7 плана.

**Готово, когда** план лежит в `plans/YYYY-MM-DD-<короткое-имя>.md`, а ревью проведено или его пропуск записан в разделе 7.

## Шаг 7. Итог и одобрение

Покажи четыре блока:

1. **Путь и глубина** - и почему, одной строкой.
2. **Итог в 5 строках** - что пользователь получил.
3. **Файлы**, которые ты создал или изменил.
4. **План** - результат, число фаз, границы и лимиты - и просьба одобрить.

Одобрение записывается в план (кто, когда, какой объём), статус - «одобрен», дальше исполнение по `docs/workflow.md`, раздел 6. До одобрения код, установка зависимостей и коммиты ждут. План разрешает коммиты - первым идёт коммит результата старта: `CLAUDE.md`, `CONTEXT.md`, `docs/architecture/overview.md`, план, а ядро и разделы `business/` - только если `business/` в git (приватный репозиторий). Не разрешает - перечисли эти файлы в checkpoint плана как незакоммиченные.

## Режим IMPORT - код или документ архитектуры

1. **Изучи проект:** `README`, манифесты, структуру папок, точки входа и главные экраны, схему данных (миграции, модели), тесты, `docs/`. Для документа архитектуры - цель, границы, компоненты, интеграции.
2. **Покажи картину одним абзацем:** что делает, для кого, что реализовано, что обещано, но не сделано, есть ли платежи, на каком стеке.
3. **Шаги 2-3:** приватность, затем ядро по фактам из кода со ссылкой на источник. У проекта уже есть бизнес-документы вне `business/` - ядро ссылается на них, второй мозг рядом не заводится. Факт из кода - факт о коде (`docs/workflow.md`, раздел 2). Вопросы - 5-7, варианты ответа из увиденного: тип проекта, цель сейчас, каналы; для коммерческого - ещё конкуренты.
4. **Шаг 4** для выбранной глубины. Цены из кода - в `products/pricing.md`, цвета и шрифты из стилей - в `assets/brand-guidelines.md`.
5. **Reality Check по коду:** 2-3 пробела - незавершённое, противоречивое или без видимой бизнес-причины.
6. **Раздел 2 `CLAUDE.md`:** фактический стек и команды сборки, тестов и линтера из манифестов. Документ архитектуры уже есть вне `docs/architecture/` - запиши его путь туда же: это канонический документ.
7. **Шаги 6-7.** Первый план - по главному пробелу из Reality Check.

## Правила во всех режимах

- Цель проекта выясняется раньше деталей стека.
- Путь и глубина видны пользователю вместе с обоснованием, и он может их сменить.
- Пользователь сказал «быстро» - ревью плана M можно пропустить, если риск мал и пользователь согласен; ревью плана L - нет.
