# Правила безопасности

> Этот файл — обязателен для прочтения Claude Code в каждой сессии. Нарушение = блокер.

## Секреты

### Что считается секретом

- API-ключи (Anthropic, OpenAI, платёжные провайдеры, аналитика)
- Токены доступа (GitHub, Telegram, Slack)
- Строки подключения к БД (`DATABASE_URL`, `REDIS_URL`)
- Webhook secrets, JWT secrets
- Пароли любого вида
- Приватные ключи (`.pem`, `.key`)

### Жёсткие правила

1. **Не читай `.env`, `.env.local`, `.env.production` целиком.** Если нужно одно значение — спроси пользователя или прочитай конкретную строку через `grep`.
2. **Не печатай содержимое секретов в чат.** Никогда. Даже частично. Даже «для проверки что они подгрузились».
3. **Не хардкодь секреты в код.** Только через `process.env.VARIABLE_NAME`.
4. **Не коммить файлы с секретами.** Файл `.env*` уже в `.gitignore` — не убирай его.
5. **Не вставляй секреты в URL** (например, `https://user:password@host/`). Используй заголовки.
6. **Не передавай секрет в одной строке с командой:** `curl -H "Authorization: Bearer sk-xxx"` — нет. Используй переменную окружения.

## .env файлы

- В репо лежит **только** `.env.example` со списком имён переменных без значений.
- Реальные `.env` создаёт пользователь сам у себя на машине / на хостинге.
- Если пользователь просит «создай .env с моими ключами» — отказываем и объясняем почему: ключи не должны попасть в репо или в логи Claude.

## API-ключи

- Все ключи — только через Environment Variables хостинга (Vercel / Railway / Amvera).
- Ротация ключей — раз в квартал минимум. Если ключ засветился — сразу.
- Серверные ключи **не** должны попадать в код, который выполняется в браузере. В каждом фреймворке есть конвенция «публичных» env-переменных: в Next.js — префикс `NEXT_PUBLIC_`, в Vite — `VITE_`, в Create React App — `REACT_APP_`. Всё, что без публичного префикса — серверное. Проверяй принадлежность ключей к этим группам.

## Деплой

- Перед деплоем: прогон проверок выбранного стека (линтер + сборка + тесты, если есть). Команды зависят от стека — см. `.claude/rules/deployment.md`.
- Не деплой с `--force` без согласования.
- Не делай прод-деплой в пятницу вечером без причины.
- Превью-деплои (preview branch) — нормально и безопасно.

## Опасные команды (запрещены без явного «да»)

- `rm -rf` любого вида
- `git push --force`, `git push -f`, `git push --force-with-lease`
- `git reset --hard`
- `git clean -fd`, `git clean -fdx`
- `curl ... | sh`, `wget ... | bash` (выполнение неподписанного скрипта)
- `sudo rm`
- `pnpm publish`, `npm publish`
- `DROP TABLE`, `DROP DATABASE`, `TRUNCATE` в SQL без согласования

## Скиллы, MCP-серверы и плагины

Скилл, MCP-сервер и плагин Claude Code - чужие инструкции и код, которые выполняются с правами пользователя. Перед установкой из непроверенного источника - проверка по `docs/prompts/install-skill-safely.md`: исходники читаются целиком, вердикт «безопасно / подозрительно / опасно». Ставится только «безопасно» и локально в проект, не в `~/.claude/`.

## Публичный репозиторий и business/

`business/` - реальные данные о клиентах, ценах и экономике. Проверка приватности проходит **до первой записи** бизнес-фактов:

1. Узнай у пользователя, приватный ли репозиторий и останется ли он приватным. Не знает - считай публичным.
2. Посмотри, что уже в git: `git ls-files -- business`, и куда смотрит `origin`: `git remote -v`. `origin` указывает на публичный шаблон `smyslokod-starter` - скажи пользователю завести свой репозиторий и сменить `origin`, иначе его push уйдёт в чужой репозиторий.
3. **Приватный** - `business/` остаётся в git как источник истины.
4. **Публичный или неизвестно** - добавь в `.gitignore` строку `/business/` (с косой чертой в начале: без неё правило скроет и формы `templates/business/`), сними папку с учёта `git rm -r --cached -- business` (файлы на диске остаются) и проверь две вещи: `git check-ignore -v --no-index business/INDEX.md` показывает правило, а `git check-ignore -q --no-index templates/business/audience/avatar.md` возвращает код 1 - формы не скрыты (без `--no-index` команда не видит правил для файлов под учётом git). Предложи сразу отдельный коммит этих двух изменений: до коммита снятие с учёта живёт только в индексе, и `git reset` вернёт папку под учёт. Скажи пользователю: история `business/` в git теперь не хранится, резервную копию папки он делает сам.
5. Запиши результат в ядро `business/INDEX.md`, строка «Приватность».

`.gitignore` не вычищает то, что уже попало в историю git, резервные копии и транскрипты. Секреты и персональные данные клиентов в `business/` не хранятся ни в каком случае.

В публичном репозитории `plans/`, `retrospectives/`, `CLAUDE.md` и `CONTEXT.md` тоже уходят в git: в них пишется только то, что можно опубликовать. Цифры, клиенты и цены - ссылкой на файл `business/`, а не копией.

## Что делать при инциденте

1. Если секрет утёк (попал в коммит / в чат / в скриншот): **немедленно отозви ключ** в провайдере, а потом разбирайся.
2. Если случайно сделан опасный коммит — `git revert <hash>` (не `git reset --hard`), это безопасный откат.
3. Если попал в репо — потребуется `git filter-repo` или BFG, согласовывай с пользователем.
