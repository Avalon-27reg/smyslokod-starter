## 8. Метрика успеха

Как поймём что план реально сработал. **Одна цифра** или одно событие. Не «всё стало лучше».

## 9. Challenge Loop (заполнить ДО написания кода)

3 вопроса. Ответы должны быть конкретными, не «да» и не «вроде да».

1. **Решает ли это задачу из блока 1?** Конкретно: ___
2. **Это лучший путь?** Какие альтернативы рассматривались и почему отброшены: ___
3. **Нет ли «кода ради кода»?** Каждый файл и абстракция в плане оправданы текущей задачей: ___

Если хоть один ответ «не уверен» — не приступать к коду, обсудить с пользователем.

## 10. Self-Audit (заполнить ПОСЛЕ реализации, до коммита)

Для каждой фазы — пройди по acceptance criteria из «Метрики успеха» и блока «Цель». **Без оправданий.**

- [ ] Цель из блока 1 закрыта (не «частично» — закрыта).
- [ ] Метрика успеха проверена руками / тестом.
- [ ] Никакой работы не отложено с пометкой «pre-existing» / «out of scope» / «доделаем потом» (если отложено — это **новый план**, не строка в этом).
- [ ] Тесты / линтер прогнаны и зелёные. Если красные — это не «известная проблема», это блокер.
- [ ] Нет изменений, которых не было в плане. Если есть — добавить в «Сделано» или откатить.

## 11. Impact Analysis (обязательно для L, опционально для M)

Что в проекте могло поломаться от этих изменений?

- **Зависимые модули:** какие файлы импортируют изменённое? Ручная проверка / тест.
- **Контракты API / БД:** изменился ли формат запроса/ответа/таблицы? Совместимо ли со старыми клиентами?
- **User-flow:** все ли пути пользователя через изменённую часть проверены? Минимум: golden-path + 1 edge case.
- **Конфиги / env:** появились ли новые переменные? Обновлён ли `.env.example`?
- **Регрессии:** что-то рядом стало работать иначе? — это **поломка**, а не «нюанс».
